# 寫 `.claude/agents/*.md` 定義檔

定義檔是可以重複使用、不綁定特定任務的 system prompt。worker 模板裡的「已知」「已排除」「目標值」是每次任務才有的東西，寫進定義檔，下一個任務就會套用到錯誤的事實，所以這些留到每次派工的 prompt 再寫。

## 寫什麼

- **description**：寫這個 agent 做什麼動作、在什麼情況下該叫它。主 agent 只靠這一段決定要不要派它，所以寫使用時機和它會做的動作。
- **tools**：只給需要的工具。稽核、調查類的 agent 不需要 Edit/Write。只要給了 Bash，它仍然能寫檔和刪檔，所以內容裡要另外寫明：專案內的檔案保持原樣，腳本只寫在 scratch 路徑。不需要跑指令的 agent，連 Bash 都不給。
- **內容**：這類工作要達成的結果、最常見的陷阱、該從哪些原始資料開始、怎麼驗證結論、回報格式（每一項標明已驗證或推測）。方法寫成「慣用的起點」，讓 agent 依每次的證據調整。
- **派工沒給目標時的預設值**：例如「派工 prompt 沒有指定目標時，以 <這類工作合理的標準> 為準，並在回報中提出建議的目標值」。
- **環境不確定時的寫法**：定義檔無法事先知道每次執行的環境能不能 build、能不能連實機，所以寫成條件式：「有就用；做不到就回報缺口，並給出派工者可以自己執行的指令」。

## 骨架

```markdown
---
name: <描述工作的名字，例如 shader-variant-audit>
description: <做什麼動作，例如「稽核 shader variant 數量並找出來源」>。<什麼情況下使用>。
tools: Read, Grep, Glob, Bash
---

## 要達成的結果
<這類工作做好時，派工者能拿結果做什麼>

## 做法
1. 先確認前提：<這類問題最常見的錯誤假設>；不成立就停下來回報。
2. 從原始資料開始：<第一手來源，以及取得方式；拿不到時怎麼辦>
3. 慣用的起點：<分群、對帳、二分法、量測…>；證據指向別的方法就換。
4. 常見陷阱：<逐條列出>
5. 驗證：<什麼外部證據能證明結論>

## 邊界
- 專案內的檔案保持原樣，也不觸發 build，除非呼叫者明確要求。腳本和暫存檔放在 <scratch 路徑>。
- 拿不到的資料列為缺口，不推測補上。

## 回報
結論／證據（可以直接重跑的指令與路徑）／驗證結果／未驗證與缺口；每一項標明已驗證或推測。
```

## 寫完怎麼驗證

自己對照清單看一遍仍然算自評。要用外部證據驗證，做這兩件事：

1. **試跑一次**：用這個定義檔，對目前的專案做一次真實任務（稽核類就做一次唯讀稽核），看產出是否符合回報格式、有沒有越過邊界。
2. **測試觸發**：寫 3–5 句使用者實際會說的話（包含 1–2 句不該叫到它的近似說法），確認主 agent 會不會在對的時候派它。
