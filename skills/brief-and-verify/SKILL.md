# Brief & Verify：交辦要有野心，完成要有證據

模型做得到的，常常比我們交辦的多。交辦時往三個方向推，它就能做得更高、更深、更廣：

- **往上（Altitude）**：交辦真正要的結果，以及結果之後想發生什麼。「修這個 crash」背後要的是「這條流程不再 crash」；一份資料調查背後要的是「明天能決定 rollback 還是 hotfix」。目的寫出來，worker 才會去追同一個根因造成的其他問題，也知道結論要回答到哪一層。
- **往深（Depth）**：要求這個領域最好的人會用的原始資料、方法和工具，給一個有野心的目標，請它拿原始資料挑戰既有的認知。你不必先知道頂尖做法是什麼，worker 通常知道；你要做的是要求它用上。
- **往寬（Range）**：把產出的名詞換成動詞，問「哪些領域每天都在做這件事」，借它們的方法。例如「crash 調查」換成「從事故紀錄找出是哪個變更讓失敗率上升」，就能借流行病學的做法：比較暴露組和非暴露組、檢查混淆因子。

只有一件事不能交給做的人自己判斷：做完了沒有、做對了沒有。模型很容易說服自己已經完成，所以完成與否由外部證據決定，也就是由沒參與製作的一方重跑、重算。驗收越可靠，前面越能放手讓 worker 自己找方法。

這套做法疊在你平常的判斷上。這個領域有哪些陷阱、要拆成幾條線、哪裡要保守，照常判斷。

## 1. 誰來做、驗收多嚴

| 答錯的代價 | 驗收方式 |
|---|---|
| 主要風險能用一個「改錯就會失敗」的檢查抓到 | 你自己重跑那個檢查，不採信 worker 回報的「通過」 |
| 主要風險要靠判斷才能確認 | 另開一個 verifier |
| 不可逆、要上線、牽涉金額或機率、要交給第三方，或前提本身可能是錯的 | 紅隊先試著推翻，再交給 verifier |

確認檢查真的「改錯就會失敗」：在修正前的程式碼上跑一次看它失敗，或故意改錯一處看它抓到。修正前或前一版的程式碼、設定，在 prompt 裡寫明怎麼取得，而且不動使用者的工作樹：`git worktree add` 到 scratch、`git show <rev>:<path>` 輸出到 scratch，或由你先備好一份複本；不用 checkout、stash 切換。編譯和既有測試通常抓不到邏輯改錯。worker 自己跑測試、重現、模擬，是它邊做邊修的回饋；驗收的證據要由沒參與製作的一方取得。

**誰來做**：你已經有脈絡、自己做半小時內完成，就自己做，因為把對話重寫成冷啟動 prompt 常常比做完還貴。代價高的工作自己做也要另外開 verifier。其他情況交給 worker。

**成本與期限**：紅隊和 verifier 要等 worker 做完才能開始，完整流程大約是 2–3 倍時間。開 3 個以上 agent 前，用一句話告訴使用者預計要多久。有期限時，平行線一回來就先交一份標明「推測」的初步結論，並先說好驗不完的備案：期限前來不及驗完時，可以先上哪個治標的做法、它不能解決什麼，由使用者決定。

**兩種特殊情況**

- 使用者明確要開 agent，但任務其實很小：開一個 worker，prompt 寫三四行（目標、來源、已知陷阱、回報出處），回來你自己核對來源。
- 任務本身就是驗收別人的產出（「agent 說修好了，幫我確認」）：你站在 verifier 的位置，用 1–2 種彼此獨立的方法驗，由你裁決。原 agent 寫的測試是被檢查的對象；另外依規格寫自己的測試，並確認它在修正前會失敗。

## 2. 派工前：準備只有你知道的事

worker 是冷啟動，看不到這段對話。方法、工具和領域知識它自己有；它查不到的，由你準備好：

- **使用者的目的和限制**：結果要拿去做什麼決定、有沒有期限。
- **已經排除的方向，以及怎麼排除的**。附上理由，worker 才能判斷證據是否值得重新打開它。
- **事實與實際生效的版本**：檔案位置、資料 schema、專案版本、git status、server 有沒有覆蓋設定。這些你讀幾秒就能確定，先讀好寫進去；repo 和資料裡查不到的才問使用者。寫成事實的句子要對得上原始檔，推出來的標成推論，因為 worker 會把 prompt 當成真的。
- **這次最可能出錯的地方**：讀資料和程式時，你會看到只有這份資料、這個版本才有的風險，例如欄位有兩種讀法、設定實際生效的時間和檔案上寫的不同、某個 runtime 版本的事件順序。把它們寫成 worker 要做的具體檢查。這是主 session 最有價值的貢獻：一般領域知識 worker 自己有，但它還沒讀過這份資料。
- **環境**：worker 需要的工具和資料拿不拿得到（`which Unity`、`dotnet --version`、`adb devices`、資料庫權限）。補不了就寫進 prompt，讓它知道要改用什麼、哪些結論會標成未驗證。用替身（stub、mock、模擬器）重現時，要求它照官方實作的呼叫順序和行為，並列出和真實環境可能不同的地方。

**高風險的調查，拆成方法彼此獨立的平行線**。例如一條從觀測資料出發，一條刻意不看資料、只從規格或程式碼推算理論值，避免先看到答案再去湊。不同方法得出一致的結論，本身就是外部證據。線的數目看能多拿到哪一種獨立證據：問題範圍窄、紅隊本來就會用自己的方法重做一次時，一個 worker 就夠。

**組隊不只為了挑錯。** 成果要交給人看時，可以加一條線做讀者那一側的事，例如找出最可能讓讀者誤解或不信的三處，補上證據。

**另一家的模型**：和你不同家的模型盲點不同，最適合當一條獨立的分析線，或當 verifier、紅隊來驗你的產出。「另一家」以你自己為準：你是 Claude 就找 Codex 或 Gemini，你是 Codex 就找 Claude 或 Gemini，你是 Gemini 就找 Claude 或 Codex；同一家換型號不算。使用者只說「找另一個模型交叉驗證」時也照這個挑。交辦方式和 worker 一樣，它同樣是冷啟動；當 verifier 時同樣只給結論、操作定義和原始資料。

派之前先確認本機有哪些 CLI（`command -v` 或 `where.exe`），再查 [references/external-agents.md](references/external-agents.md) 的呼叫方式、權限模式和它執行指令用的 shell；表上沒有的工具以它的 `--help` 為準，先實跑一次。寫給它的 prompt 只用它那個 shell 跑得起來的語法，例如它在 PowerShell 執行就不寫 heredoc。唯讀模式通常不能執行指令或寫檔，只適合判斷型驗收；要重算就用寫入範圍確實被限制在 scratch 的模式；別家都沒有這種模式時，跨家那條只做判斷型驗收，重算交給有隔離的一方（可以是同一家），並標明這一點。在背景執行，回報寫成檔案，你讀原文。本機找不到別家時，明講這次的驗收少了哪一種獨立性。

兩邊結論不同時，你依證據裁決，不投票；不一致的地方就是下一步要查的。

## 3. 寫 worker prompt

```
## 目標
<要的結果、結果之後想發生什麼，以及為什麼重要>
<有野心的目標值，並說明這是做得到的>

## 完成標準
<什麼外部證據能證明做對了：可重現、可重算、改錯時會失敗的測試；批次修改要能對帳，每一處都有歸類>

## 你需要知道的事
- 已知：<主 session 查好的事實、實際生效的版本>
- 已排除：<方向，以及怎麼排除的>
- 未知：<查不到也問不到的；請在回報裡說明它對結論的影響>
- 位置與環境：<路徑、可用和不可用的工具>

## 邊界
<授權範圍；不能碰的東西和原因>

## 做法
動手前先寫下你的計畫：這個領域最好的人會做哪些我沒要求的事、他們從哪些最原始的材料開始、用什麼方法和工具、這類結果最常在哪裡出錯，以及除了你和我之外，什麼能證明結果是對的。然後照計畫做，邊做邊用工具取得回饋；證據指向別的方法就換，並說明理由。
<這次最可能出錯的地方，寫成要做的檢查>
發現 <嚴重問題> 就先停下來回報。

## 回報
結論／每條主張的操作定義（公式、篩選條件、資料範圍）／證據（可直接重跑的指令與路徑）／未驗證與缺口／被推翻的假設；每一項標明已驗證或推測。結論是「沒問題」時，說明以目前的證據能排除多大的問題，例如「以這個樣本量，可以排除大於 0.3pp 的偏差」。
```

寫的時候：

- **要求動作。** 身分設定（「你是資深效能工程師」）通常只換掉語氣和術語；「用 Profiler 錄一段 capture，列出每幀成本最高的三項並附數字」才會換掉方法。想不出該要求什麼動作時，問「哪些領域每天都在做這件事」。
- **有野心的目標值是方向，不是門檻。** 寫「冷啟動壓到 2 秒內，這做得到」比「盡量加快」更能逼出好方法。驗收只看主張成不成立、完整性有沒有對上，已經證實的 35% 改善不會因為沒到 2 秒就被判失敗。
- **前提分兩種寫。** 前提不成立、後面就全部白做的，寫成「不成立就停下來回報」。前提不成立本身就是答案的（「這個落差是 bug，不是波動」），寫成要驗證的步驟。
- **陷阱寫這次的。** 「duration 欄位可能是毫秒也可能是秒，先用已知長度的事件判斷」這種才寫；「注意資料品質」這類一般提醒留給 worker 自己列。prompt 越短，重點越清楚。
- **嚴重問題要早點知道時**（玩家被少付錢、資料遺失），寫「發現 X 就先停下來回報」，或拆成幾段、每段都回報，因為 subagent 只在結束時回報一次。
- **範圍有模糊地帶時，派工前用一句話問使用者**，例如 LogWarning 算不算、Editor 腳本算不算。問不到就照字面範圍做，有疑慮的列成清單。

**會改變東西的工作（改檔案、合併、上線）**：理解和調查盡量往上推，動作停在使用者授權的範圍。改錯造成的行為變化比漏改更難發現，所以這裡保守，而且每一步都要能收回：

- 明確授權的直接做；有疑慮的附建議 patch 讓使用者決定；範圍外的列成清單。使用者還沒提交的修改屬於使用者，保持原樣。
- 動手前留一份能照位元組還原的備份；只存 hash 只能發現被改，不能還原。
- 超出原本範圍的修改（同根因的其他位置、順手的改善）放在獨立的 commit 或 patch，使用者才能單獨拿掉。大量修改依目錄或類型分批，平行的線各自負責不重疊的檔案。
- 完成標準除了「問題消失」，再寫一條改完後必須成立的狀態，例如「鎖的計數回到開始前的值」「沒按 Skip 時事件序列和修正前完全一樣」。只看問題消失，抓不到多解一次鎖這類新問題。

## 4. 執行與驗收

1. **worker 產出**，彼此獨立的線平行跑。
2. **紅隊攻擊**（答錯代價高才有）。
3. **修正被推翻的項目**：只需要改敘述就自己修；要重算或改程式，把被推翻的項目和證據交回原 worker 續做（它已有脈絡）；原 worker 無法續用時才開新 worker，給它原 prompt、原產出和被推翻的項目。修完直接交給 verifier。
4. **verifier 驗收**：給它結論、每條主張的操作定義（從 worker 回報原文照貼）、完成標準、原始資料的位置。推導腳本、中間計算和紅隊紀錄不給，讓它從頭自己算，才不會被同一條思路帶著走。
5. **verifier 判定不通過**：你先看雙方的證據。錯在產出，退回修一次；錯在 verifier，修它的 prompt 開一個新的重跑，不續用原 verifier，免得帶著原本的框架。修過一輪仍不通過就停，向使用者回報「未驗證」並附上證據。

**派給誰**：紅隊和 verifier 要自己重跑、重算、寫腳本，所以依 agent 的工具和規則挑，不看名稱。名稱叫 verifier、reviewer 的 agent 若是唯讀（沒有能執行指令的工具、描述寫 read-only，或規定不得建檔），只能做判斷型驗收或核對 diff，它的結論算判斷，不算重算；要重算就派能執行指令、能寫 scratch 的 agent，並在 prompt 指定 scratch 路徑。計畫裡寫明用什麼派出：你所在工具的 subagent 功能（例如 Claude Code 的 Agent 工具、Antigravity 的 `invoke_subagent`），或哪個外部 CLI。沒有 subagent 功能就用外部 CLI；兩者都沒有就自己做，並標明這不是獨立驗收。

**紅隊**

```
以下是一份產出，以及它依據的原始資料位置。
請找出最可能出錯的地方，並實際試著證明它錯了：
- 挑至少 3 個最弱的主張或改動（推論跳躍、樣本太小、沒有驗證、邊界情況）；大量修改依類型抽樣，並回報抽樣覆蓋率。<這類任務常見的陷阱>
- 用原始資料或實際執行去推翻每一個。自己寫腳本重算，不沿用產出裡的腳本。
- 回報哪些被推翻（附證據）、哪些經過攻擊仍然成立、哪些無法判定。
只談對錯。產出和專案內的檔案保持原樣，腳本寫在 <scratch 路徑>。
```

**Verifier**

```
以下是一份產出的結論、每條主張的操作定義、完成標準，以及原始資料的位置。你沒看過它的製作過程，這是刻意的。
逐條自己重跑、重算或重現，以你取得的證據為準。
每一條回報：通過／不通過／無法驗證，並附上證據。產出和專案內的檔案保持原樣，腳本寫在 <scratch 路徑>。
```

## 送出前檢查

- [ ] 目標寫的是結果，以及結果之後想發生什麼
- [ ] 完成標準是外部證據，驗收強度符合答錯的代價；有期限時有初步結論和備案
- [ ] 寫成事實的句子對得上原始檔；這次最可能出錯的地方已寫成檢查
- [ ] 每一句都答得出「這句幫 worker 做出什麼」
- [ ] 會改變東西的動作停在授權範圍內，而且每一步都收得回來
- [ ] verifier 拿到操作定義，沒拿到推導過程；要重算的角色派給能執行指令、能寫 scratch 的 agent

拿不準要寫到多具體時，讀 [references/examples.md](references/examples.md)，裡面有效能優化和資料調查兩個完整範例。寫 `.claude/agents/*.md` 定義檔時（只適用 Claude Code），讀 [references/agent-definitions.md](references/agent-definitions.md)。

## 反饋紀錄

流程結束時，若發生可觀察的事件（skill 某處讓派工卡住或出錯、紅隊推翻了什麼、verifier 抓到什麼），在最後回報附一筆草稿，問使用者要不要記到 `~/.agents/skill-feedback/brief-and-verify.md`；使用者回「記」才追加。檔案不存在就先建立，開頭寫上收錄規則：一行一筆，只記可觀察的事件（含正面的），不記主觀評價；觀察欄附原文摘錄，不只放 scratch 路徑；欄位為「日期｜任務｜對應 skill 處（§／行號）｜觀察（摘錄）｜誰發現｜實際耗時｜狀態」。檔案已存在就照它開頭的規則。
